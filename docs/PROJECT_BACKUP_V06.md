# MVG v0.6 — Portable Project Backup & Restore

Updated: 2026-11-05

## Goal
Let the owner explicitly export MVG project data and downloaded media to an Android file-provider destination, then import it into the same or another MVG installation **without overwriting existing projects**.

This protects against losing new project data while testing future APKs. It does not retroactively recover app-private data from an already uninstalled v0.5 app.

## UI
- Settings → PROJECT BACKUP & RESTORE → Create complete ZIP backup.
- Android's system file picker chooses the target location; there is no custom storage permission or app-managed cloud upload.
- Settings → Restore ZIP (add as new projects) → select an MVG archive.
- Both actions show confirmation dialogs and operation status. Expensive media file copying runs on a background executor; running scene rendering and backup/restore cannot start simultaneously.
- Import creates **new project IDs**, clip IDs, movie IDs and avatar IDs. Project titles get the suffix "(restored)".
- The app does not import authorization state, API keys, Google access tokens, signing keystores or stored local credential encryption keys.

## What's in the ZIP
- projects, clip metadata/storyboard order, drafts, AI Director messages, avatar library metadata, exported movie metadata;
- locally available project clip MP4s, avatar JPEG/PNG images and rendered movie MP4s, if they exist in app-private media storage;
- JSON manifest with schema version and per-file SHA-256 digests and sizes.

Missing local video files aren't silently re-created: restored clips without media return as Check again (when their operation/GCS URI exists) or Needs review, and Google Cloud reauthorization may be required to retrieve the output. The original generated video and credits are not regenerated by restore.

## Security and integrity
**IMPORTANT: the v0.6 ZIP backup is NOT encrypted.** It can include personal photos, prompts, and videos. Keep it in a private device folder or an encrypted vault; do not share this ZIP publicly.

The restore engine rejects:
- absolute/parent-relative, unexpected and duplicate ZIP entry paths;
- missing/invalid manifest or unsupported schema;
- file-integrity SHA-256 mismatches, missing media, unreferenced extra entries;
- media files above 512 MiB each, total extracted media above 2 GiB, excessive numbers of records and files.

Media is first extracted to an app-private temporary folder, checked and then copied to *new* random private filenames. The final metadata commit adds existing + restored objects without deleting older data. Partial files from a failed restore are cleaned up; restore attempts may still consume temporary device space.

The supplied archive is trusted only as project data, not code; it cannot set authentication state, redirect application network endpoints or grant Google Cloud permissions. Restore does not charge for a new Veo generation.

## Source implementation
- ProjectBackup.kt: manifest writer/ZIP integrity-checked reader, bounded streaming, add-only restoration.
- StudioStore.kt: backup snapshots that exclude secrets; transactional-ish metadata commit and durable files.
- MainActivity.kt: Android Storage Access Framework CreateDocument/OpenDocument pickers, import/export workflow and safety dialogs.
- ProjectBackupTest.kt: basic allowed-entry and ZIP path traversal tests.

## Important limits
- This is **manual**, not scheduled automatic backup.
- The archive format is v1 and import only supports the same v0.6 schema.
- Unencrypted exports should be kept private; password-encrypted backups are a future enhancement.
- Up to 2 GiB total media, 512 MiB per source media file, 1000 files and bounded metadata; larger projects will be refused rather than silently truncated.
- Google login must be performed again after restore; restored projects do not automatically gain model access or promotional credits.
- End-to-end Android device testing (real SAF provider, large archives, interruptions, crash recovery and cross-device import) is still required. GitHub compile/unit tests alone cannot validate these.
- If your installed MVG v0.5 APK has a different signature from v0.6, Android may reject an in-place update. **Never uninstall an older MVG with irreplaceable projects or media without a verified backup path.** v0.5 does not include portable backups. Stable signing requires a user-controlled private keystore in GitHub Secrets; it is not magically present.
